# OVL_0025 +0411: translated, evidenced LOAD MONSTER wrapper (evidence only; no credit proposed)

This raw CPU body, `OVL_0025_0411` (unit 0x25, entry slot 5), allocates the 11Dh-byte monster record with GetMem, calls the unit-0x6F stub `007C:003E` (entry 6, `OVL_006F_0EC4`) with the record and
the block id, and copies two chain pointers out of the record into its caller's output variables. It is the wrapper whose one unready callee is the 0EC4 body of #1367. This change adds the model, its
checker, its native harness and this document. It proposes **no strict row, no identity row and no manifest row**; par-e accepts or refuses.

## What the body does

Frame after the far call: `[SP]` IP, `[SP+2]` CS, `[SP+4]` the far address A6 of an output far pointer, `[SP+8]` the far address AA of an output far pointer, `[SP+0Ch]` the far address AE of the
record variable, `[SP+10h]` the block id (a word slot, read as a byte). RETF 0Eh.

1. `PUSH BP; MOV BP,SP; SUB SP,4` (flags as `SUB`).
2. `AE^ := nil` (two word stores through `LES DI,[BP+0Eh]`).
3. `GetMem(11Dh)` (`0AF8:023F`); `AE^ := DX:AX`.
4. Push the id (`AL := [BP+12h]`, AH as it stands), then AE^'s segment and offset; `LCALL 007C:003E`.
5. `AA^ := R+C8/CA`; `A6^ := R+7F/81`, with R := AE^^ re-read through `LES DI,ES:[DI]` after the callee returns.
6. `MOV SP,BP; POP BP; RETF 0Eh`. No value is returned in a register on purpose; AX/DX hold the last field read.

## The stub 007C:003E, declared exactly

This is the same mechanism as the roll stub of the 0EC4 audit (`00B0:0048`), for a different unit. The call is a **real, fixup-backed far call**: the segment word at `CS:0447` is an `lcall_segment` entry of unit 0x25's
table reading **007C**, which is **unit 0x6F's run-time stub segment** (`memory_segment` 124, sequential check true). The offset **003E = 20h + 5 x 6** is entry 6 of that stub table, and unit 0x6F's entry 6 is `+0EC4`.
In the game the overlay manager builds that table at run time as five-byte stubs dispatching through INT 3Fh; **the expanded image does not contain the run-time stub** (the five bytes at 007C:003E there are
`06 07 08 09 00`).

The substitution, identical in the oracle and in the C model: **the INT 3Fh overlay-manager dispatch is not executed.** The five bytes at 007C:003E are replaced by a far JMP (`EA C4 0E <lo> <hi>`) to the loaded unit 0x6F
`+0EC4`. The C model reads the stub segment word live, requires the stub entry to be `EA` + offset `0EC4` (else CODE, with IP at the call and before its return frame), takes the target segment from the stub's own bytes, and
enters the 0EC4 model. **What this pins:** the call frame (R's offset and segment, the id) and what 0EC4 does with them. **What it does not pin:** the overlay manager, its stub construction, or that unit 0x6F is resident when
a real game calls; and the roll stub inside 0EC4 keeps its own declaration (`OVL_006F_0EC4_CPU.md`).

### Findings made while building the audit

- **The wrapper's pointer accesses must go through the bus.** The first version read and wrote through the caller's pointers as flat RAM. The case that puts AE inside the record GetMem returns makes the callee overwrite AE's own bytes, so the
  wrapper dereferences a garbage pointer; that pointer fell into the EGA aperture, where the oracle read a plane byte (`31h`) and the model read flat RAM (`5Ah`). The model now uses the bus for those accesses, and the mutant that bypasses it is caught by exactly that case.
  The 0EC4 body itself still keeps its flat-RAM contract (stated in its document); this wrapper is where a garbage pointer can first reach the aperture.
- **`LES` reads its two words physically contiguous, not wrapped at 64 KiB** (the corpus convention, as Unicorn does it), while an explicit `MOV ES:[DI+2],DX` wraps the offset at 16 bits. With AE straddling offset FFFFh the wrapper therefore reads back a different pointer than it
  stored. The case `out-ae-straddles-64k` runs the differential only (the independent statement assumes no straddle); the pinned DOSBox-X reads that segment word wrapped, so this is a declared split on that one case, not a measurement of the original CPU.
- Entry SP bound: 0EC4's measured minimum 09F4 plus the wrapper's own 10h pushed is 0A04; the audit's `sp-min` case runs exactly there.

2. The environment services are scripted or modelled, not real; every unlisted access is an environment refusal (counted, zero). The EGA is an independent Python device; BIOS and DOS are the scripted services.
3. The three name constants and the message literal are read from the bytes; no game text is in the repository.

The 0EC4 audit's `run_unicorn` and `run_c` were generalised for a wrapper (extra known segments, extra named entries, a watched span, the inner BP, and the diagnostic and status types are parameters, all defaulting to the old behaviour); the 0EC4 checker still builds and its cases are unchanged.
