# U3B0 entry4 `+0DC7`: node-head branch after two SYSTEM copies

`src/recovered/overlay_u3b0_entry4_node_gate_0dc7.c` executes the
three original DOS v1.3 `GAME.OVR` instructions at `+0DC7..+0DCE`.
It stops at either `+0DCF` for a null node head or `+0DEA` for a
non-null head, before either branch destination executes. Its input
frame is generated by **both** original SYSTEM `0AF8:0B25` copies
returning; no copy output is fabricated. This is a bounded branch
gate, not a complete entry4 translation or natural gameplay frame.

The pre-implementation `deja "poolrad U3B0 entry4 +0DC7 after second
SYSTEM 0B25 return node head branch gate C ownership"` query timed
out (exit 124) and supplied no reusable claim. The predecessor
address and copy-body leads came from reviewed entry4 work at commits
`1dec2e5eadaa5bfc4840aba97426f7157d11b1b3`,
`e461f6486d06ebb22b6b9e47967009ee89e60e7d`, and
`3e5b7482c108bbb4a14ae3c227abd900b94732e7`. Local and remote
ownership scans found no other U3B0 `+0DC7` source. The unrelated
`+0DC7` documentation hit belongs to unit 0x31.

The C model reads the head offset at `SS:[BP+0x14]`, ORs the head
segment at `SS:[BP+0x16]`, sets the observed logical flags, and
chooses the original branch destination. It writes no RAM. AF after
`OR` is architecturally undefined; the full-flags comparison here is
against Unicorn's original-byte result and makes no native AF claim.

The oracle starts at entry4 `+0D9A`, executes the original first and
second `0AF8:0B25` bodies and their `RETF 10` returns, then captures
all RAM and CPU state at `+0DC7`. It executes the original gate and C
from the same frame. **48/48** controlled cases match every byte of
1 MiB RAM and all 14 CPU words at `+0DCF` or `+0DEA`. Cases vary
incoming SP, both Pascal string lengths including the 40-byte cap,
null/offset-only/segment-only/full node heads, and incoming flags.
Both copy output buffers, DS restoration, and returned SP are checked.
