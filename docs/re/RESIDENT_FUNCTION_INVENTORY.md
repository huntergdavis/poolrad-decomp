# DOS v1.3 resident function inventory

This is the resident half of [issue #24](https://github.com/huntergdavis/poolrad-decomp/issues/24).
It inventories directly called `START.EXE` targets without turning raw byte
patterns or compiler helpers into a game-function denominator. The address-only
JSON generated by `tools/overlay/resident_inventory.py` gives every target a
stable `RES_segment_offset` or `SYS_segment_offset` ID, its call-site offsets,
evidence, classification, and a file offset only where validated. PM owns the
overlay-candidate half and the eventual combined ledger.

## Inputs and method

| Input | Size | SHA-256 |
| --- | ---: | --- |
| `START.EXE` | 65,231 bytes | `d825df2b174675c9088ba1489488bdeebe66ad2a22943f17d3a198e60b6a07bd` |
| `GAME.OVR` | 206,105 bytes | `872964a32cef0fc32bbf83bab68b15e04ad36d59076f37b00a179dfee7928614` |

`START.EXE` has a 512-byte MZ header and a 64,719-byte resident file image.
The script rejects other hashes. It reuses the repository's
[`overlay_inventory.py`](../../tools/overlay/overlay_inventory.py) descriptor
and fixup parser, then iterates **fixup positions**. A fixup three bytes after
opcode `0x9A` identifies a far-call segment operand; the two preceding bytes
give its target offset. This avoids the non-overlapping regex scan's three
missed adjacent calls. The caller IDs, target IDs, and mapped file offsets
contain no executable or save bytes.

Prior work reused: the [overlay inventory](overlay_inventory.md) establishes
34 units and 404 public entries; the [function ledger](FUNCTION_LEDGER.md)
proposed the `-455` mapping for segments `0x464` and `0x709`; the [DOS
character trace](../formats/DOS_CHARACTER.md) identifies the `0xBA:0x1509`
party-record use and two `0xAF8` file-I/O calls. Before implementation,
`deja` queries for exact resident mapping terms found no previous inventory;
broader `deja "resident"` recalled Claude's preliminary self-relocation
analysis. That linear-model lead was checked and narrowed by the target and
instruction evidence below.

## Measured call-target partition

| Measure | Count | Interpretation |
| --- | ---: | --- |
| Fixup-confirmed far-call sites | 4,012 | Source instruction evidence; no near-call byte-scan hits included |
| Known overlay calls | 1,154 | Resolved through recorded memory segments and public stub offsets |
| Final-unit overlay calls | 7 | Inferred segment `0x428`; see below |
| Non-SYSTEM resident calls | 1,061 | 86 distinct segment:offset targets |
| `0xAF8` SYSTEM/runtime calls | 1,790 | 48 distinct targets; excluded from the game count |
| Non-SYSTEM resident targets mapped to exact `55 89 E5` prologues | 84 | Distinct file positions under bounded empirical shifts, each backed by a fixup-confirmed call |
| Non-SYSTEM resident targets without a validated file position | 2 | `RES_0A40_029C`, `RES_0A40_02FD` |
| Raw resident-image prologue hits | 132 | 48 are not among the 84 mapped called starts; their function status is open |

The 86 called non-SYSTEM targets classify as six verified game-specific, zero
verified other-library, and 80 unresolved game-or-library targets. The 48
remaining raw prologue hits have not been proved false or assigned to
functions. No two of the 84 validated targets alias the same file offset;
possible aliases or nonprologue starts among the unmapped targets remain open.
Separately, the [overlay candidate audit](OVERLAY_FUNCTION_INVENTORY.md)
reports 668 of 673 overlay prologue candidates with entry or decoded call
evidence, including 354 distinct near-call targets from 966 decoded sites;
five candidates lack listed callers. Those overlay candidates are not added
to this resident mapped-start count.

The pre-correction [`callgraph.py`](../../tools/overlay/callgraph.py) reported
4,009 sites because its non-overlapping `0x9A` regex consumed a false
byte-pattern match immediately before three real calls. The corrected scanner
and this inventory both report 4,012. The formerly omitted sites are
GAME.OVR unit `0x6f:+0x2f7` (file `0x1e2dd`, target `0xAF8:0x0B0B`), unit
`0x77:+0x1dae` (file `0x22de8`, target `0xAF8:0x0B98`), and unit
`0x7f:+0x2050` (file `0x26cd9`, target `0xAF8:0x0B0B`). Each has a relocation
on the segment word and disassembles at its exact site as `CALL FAR`. They
affect only the runtime site total. Existing lane A code was not changed.

### Final overlay unit is not resident

The last overlay unit, `0x40c`, has three public entries but no recorded
runtime segment because no following descriptor supplies it. The previous
unit `0x3d2` has runtime segment `0x3ee`; its descriptor is 918 bytes before
the final descriptor. The late-unit descriptor spacing predicts
`0x3ee + ceil(918/16) = 0x428` (eight of nine checkable neighboring late-unit
steps fit the same rule; one differs by one paragraph). Seven fixup-confirmed
calls to `0x428:0x25/0x2a` select exactly entries 1 and 2 of that three-entry
unit, whose code targets are `+0x3b` and `+0x15d`. This strongly supports
reclassifying those seven sites, formerly counted as resident, as overlay.
The shared overlay parser now records `0x428` with
`inferred_descriptor_spacing` provenance; this inventory checks that
inference rather than treating it as a recorded header value.
PM was notified in [issue #24](https://github.com/huntergdavis/poolrad-decomp/issues/24#issuecomment-6104428912)
for independent cross-check.

## Called-target file mapping

For the exact audited build, an observed target maps as
`file = 0x200 + 16*segment + offset + shift`. The shifts below are **bounded to
the listed called-target ranges**; no rule is extrapolated through an untested
gap or to a different executable. Every one of these 84 mapped targets is an
exact `55 89 E5` instruction start as well as a relocated far-call target.

| Segment | Called offset range | Shift | Mapped targets | Classification |
| --- | --- | ---: | ---: | --- |
| `0xBA` | `0x0442..0x2199` | -292 | 24 | game or linked library unresolved, except `0x1509`, `0x15F7`, and `0x2199` below |
| `0xBA` | `0x2228..0x2B88` | -316 | 13 | unresolved except verified `0x23B7` and `0x23DB` |
| `0xBA` | `0x2C48..0x2F57` | -330 | 5 | unresolved |
| `0x3F1` | `0x0000..0x02E8` | -446 | 3 | unresolved |
| `0x464` | `0x00FF..0x2A0D` | -455 | 13 | unresolved |
| `0x709` | `0x017C..0x0DD3` | -455 | 13 | unresolved |
| `0x802` | `0x025D..0x095D` | -457 | 7 | unresolved |
| `0x899` | `0x0000` | -457 | 1 | unresolved |
| `0x899` | `0x0059..0x0122` | -481 | 3 | unresolved |
| `0x8AE` | `0x00DC..0x01A5` | -489 | 2 | unresolved |
| `0xA40` | `0x029C`, `0x02FD` | — | 0 | both target file positions and game/library provenance unresolved |

The `0xBA` shifts change in three ordered target groups; using one shift for
the entire segment would lose 18 exact prologues. The `0x899:0` entry is a
useful instruction-boundary check: shift `-481` lands inside a previous
instruction, while `-457` lands on its prologue at file `0x89c7`. For
`0x8AE`, an alternate `-948` also happens to hit two prologues, but those
positions overlap the preceding `0x899` routines, one of which calls
`0x8AE:0x00DC`; the ordered `-489` positions follow that segment and decode
as distinct routines. These choices are checked only for the listed targets.

The `0x899` mapping has **moderate confidence**: all four called targets have
exact prologues, and the `0x899:0` instruction boundary rules out the shift
used by its other three targets. No loader relocation record directly proves
either shift across the segment. The `0x8AE` mapping also has **moderate
confidence**: ordered non-overlapping code favors `-489`, but a second shift
also happens to hit prologue bytes and no direct loader relocation record
settles the choice. The two `0xA40` calls have **low mapping
confidence**: their segment words are fixup-confirmed, but no unique resident
file start or game/library origin has been established; they contribute no
mapped-start count.

`0xAF8` is independently identified as the Turbo Pascal SYSTEM/runtime
segment. Its `0x0B0B` and `0x0B25` targets map to file `0xB781` and
`0xB79B`, where the instructions copy a Pascal length byte and characters.
Its `0x14FB` and `0x1502` targets map to file `0xC13B` and `0xC142`, where
adjacent routines select DOS `AH=0x3F` (read) and `AH=0x40` (write) and join
a shared `int 21h` path. These two pairs require shifts `-1290` and `-1344`
respectively, so a single segment-wide linear mapping is disproven. The
other 44 runtime targets are excluded by segment classification; their file
starts are not claimed.

## Denominator status

There are **84 distinct exact-prologue mappings under bounded empirical
shifts**: each target has a fixup-confirmed incoming call and maps to a
different resident file offset. The `0x899` and `0x8AE` shifts remain
moderate-confidence inferences, so this is a supported called-start count,
not a loader-verified exact denominator or a game-source count. The six
overlay-called resident targets promoted to *verified game-specific* are
`RES_00BA_1509` at file `0x2185`, `RES_00BA_15F7` at file `0x2273`, and
`RES_00BA_2199` at file `0x2E15`, `RES_00BA_23B7` at file `0x301B`, and
`RES_00BA_23DB` at file `0x303F`, and `RES_00BA_2E03` at file `0x3A59`:
the first three remove, append, and search character sidecar lists; the next
two test a character field and count records
on the loader-backed party list, as established by the trace and reviewed
[append](RESIDENT_SIDECAR_APPEND.md) and [lookup](RESIDENT_SIDECAR_LOOKUP.md)
translations, [field predicate](RESIDENT_CHARACTER_FIELD_ZERO.md), and
[party counter](RESIDENT_PARTY_COUNT.md) translation. The sixth checks a
character-linked table state; see the reviewed
[link predicate](RESIDENT_CHARACTER_LINK_CHECK.md) translation.
One of `RES_00BA_23DB`'s ten fixup-confirmed callers is GAME.OVR unit `0x25:+0x1e8c`
(file `0x935f`); the function ledger identifies that unit's entry 21 as
walking the party records and calling this target.
That gives a conservative **overlay-called resident game-function lower bound
of 6**; the remaining 80 called non-SYSTEM targets have unresolved game versus linked
library provenance. The two `0xA40` targets are especially plausible
low-level library calls, but their starts and ownership remain unverified.

Among directly called non-SYSTEM targets, the possible game count is 6–86.
That is **not** an upper bound for the full game: indirect calls, uncalled
routines, 48 unmatched raw prologue hits, nonprologue starts, and the still
separate overlay candidates remain unaudited. The 404 overlay public entries
overlap their unit functions and must not be added to a prologue count. No
full denominator or completion percentage is claimed here.

## Reproduce

The script reads ignored owner-supplied binaries and writes only address
metadata to `/tmp`:

```sh
PYTHONDONTWRITEBYTECODE=1 python3 tools/overlay/resident_inventory.py \
  --exe resources/DOS/POOLRAD/START.EXE \
  --ovr resources/DOS/POOLRAD/GAME.OVR \
  --json /tmp/poolrad-resident-targets.json
sha256sum resources/DOS/POOLRAD/START.EXE resources/DOS/POOLRAD/GAME.OVR
```

The script asserts the two input hashes, 34/404 overlay facts, the four
runtime instruction signatures, the final-stub inference, the call-site
partition, and all 84 mapped prologues. It fails if any of those observations
change. No original binary, disassembly, decoded string, media, or save bytes
are committed.
